## Route order

1. For discovery, use Exa `web_search_exa` with a domain-limited query. If the sandbox reports a DNS/network error OR an HTTP-level block (403/401/429/503, a Cloudflare "Just a moment..." challenge, or a WAF page), treat it as `route_state=host_retry_required` — a sandbox access-block is NOT evidence the site is down. Forum sites are almost universally WAF-protected and sandbox curl 403s while the same URL returns content over the host network (verified 2026-10-15: linux.do/nodeseek/osdev/linux.org 403 in sandbox, 200 via host reader). Retry through the Agent Reach host-network route when available; if that route is unavailable, use host web search as an independent indexed fallback and record the original error. Prepare the bilingual QUERY_PACK required by the main skill before each search request. Mark indexed results as indirect; never describe a fallback as an Exa query.
2. For Linux.do, use the local `mrsxs/linuxdo-mcp` browser-authorized route first, then the shared read-only CLI wrapper, and treat failures by class: an **expired session** (`whoami` → "登录会话已失效", or HTTP 403 "You need to be logged in") is fixed by **one** `linuxdo-mcp login` browser authorization that every agent shares — re-authorize and retry rather than switching backends, because the MCP and the wrapper read the same session and a different route would fail the same way. Other classes (Cloudflare challenge, account trust-level restrictions, 429) do fall back: the logged-in OpenCLI browser adapter, then site-limited indexed search, saving each failure before switching and recording the method. For other verified native routes, use the forum's public search endpoint or inspected search form. For public Discourse sites prefer the `discourse-forum` CLI shipped with this skill (`scripts/discourse-forum`, symlinked at `~/.local/bin/discourse-forum`) — see the endpoint section below. For the six non-Discourse communities, prefer the self-built read-only CLI shipped with this skill (`scripts/forum-cli/forum_cli.py`, exit code `75` means access blocked, not empty). Bare `/search.json?q=QUERY` remains a candidate for other Discourse hosts: verify it returns matching topic records and follow returned page/more-results fields. A latest feed or RSS is only a recent-content index. V2EX node browsing is not general full-text search.
3. Open relevant topic URLs and read the body with Exa `web_fetch_exa`; use Jina Reader when fetch does not return usable body text. Treat search snippets, titles, HTTP success, and JSON IDs as discovery evidence only.
4. Read public replies from the topic page or a verified public topic endpoint. Keep body and replies as separate read outcomes. Follow explicit next-page or continuation fields; do not infer exhaustion from a command limit or a single page.
5. When a source exposes RSS, first discover its feed URL from the site's own public page, then record the feed's actual date coverage. RSS has no comments and usually represents incremental/recent items; follow item links for full posts.
6. If a site is blocked or its route is unverified, record the exact reader, date, and failure state, then continue with site-limited indexed discovery. Do not present that fallback as native forum search.

For each forum, keep these states separate: adapter discovered, backend configured, query returned relevant topics, topic body read, replies read, and pagination exhausted for the requested query window. A Doctor status or OpenCLI catalog entry alone proves none of the latter content states. This is a point-in-time routing guide; recheck endpoints and access conditions when used.


### Linux.do 能力矩阵（2026-11-01 实测，应用层状态码）

用 MCP 自己的 curl_cffi 会话（同 impersonate 指纹 + cf_clearance）逐端点复测：

| MCP 工具 | 端点 | 应用层 | 说明 |
|---|---|---|---|
| `list_tags` | `/tags.json` | 200 | 匿名可读 |
| `list_categories` | `/categories.json` | 200 | 匿名可读（**连发多个工具时可能撞 CF 挑战/限流，单发就通**，不要误判成鉴权失败） |
| `latest_topics` | `/latest.json` | 200 | 匿名可读 |
| `top_topics` | `/top.json` | 200 | 匿名可读 |
| `category_topics` | `/c/<id>/.json` | 200 | 匿名可读 |
| `get_topic` | `/t/<id>.json` | 200 | 匿名可读 |
| `search` | `/search.json?q=` | **403** | **Discourse 站点门禁**：`errors: ["You need to be logged in to do that."]` |
| `whoami` | `/session/current.json` | **404** | 未登录时 Discourse 回 404，代码显式转成「未登录」 |

**判读规则**：Linux.do 的会话存储 `~/.cache/linuxdo-mcp/` 只有 `cf.json`（**Cloudflare clearance**，非登录态）与 `session.json`（`_t` 登录 cookie）；只有 `session.json` 存在才叫「已登录」。缺 `_t` 时按匿名身份访问公开内容——**6 个读取能力照常可用，只有 `search` 被门禁挡住**。因此：

- 渠道状态应写成「**可读（匿名 6 项）+ 搜索需登录**」，**不要**因为 `search` 失败就判定整个渠道 not_authenticated。
- 需要搜索时才做一次 `linuxdo-mcp login` 浏览器授权（授权一次、各端共享同一 `session.json`）；只读浏览不需要。
- **裸 urllib/curl 复测会全部拿到 CF 挑战页**（`cf_clearance` 与 TLS 指纹绑定），必须用 MCP 同款 impersonation 指纹才能看到应用层状态码。

### MCP 报 "Error executing tool X" 时怎么拿到真因

MCP SDK（`mcp/server/mcpserver/tools/base.py`）把工具内部抛出的任何异常统一包成 `UnexpectedToolError: Error executing tool <name>`，**原始 message 被丢弃**；真因只在 server 的 stderr traceback 末尾。宿主只拿到通用串时不能分类，必须改用 `scripts/linuxdo-read`（它提取 `server_reason` / `server_stderr`），例如：

```
RuntimeError: 无权访问(HTTP 403)：You need to be logged in to do that。（当前未登录，可调用 login 授权登录后再试）
RuntimeError: 未登录：请调用 login 工具（或命令行 `linuxdo-mcp login`）授权登录。
```
